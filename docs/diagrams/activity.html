Member flow

  • A new user branches to Register; an existing one to Authentication. Both merge on one flow into the Valid? decision.
  • invalid loops back to Login down the left margin — clear of the Register activity.
  • An account that is not yet active can only reach View Pending, which ends the flow.
  • After activation the fork runs five concurrent branches: browse, post, match, profile, matches.
  • Chat starts only when the match is accepted; the no guard bypasses the chat activity and rejoins at the join bar.
  • All branches synchronise at the join bar before Logout.

Admin flow

  • Both guards of Valid? are drawn: valid continues to the panel, invalid loops back to Admin Login with a right-angled route.
  • Four concurrent branches: user approval / status, deletion, report review, analytics.
  • Every branch reaches the join bar, so the flow synchronises before Logout.

Routing rules used in both diagrams

  • Every control flow is orthogonal (only horizontal and vertical segments) and every arrowhead lands on a node boundary — no floating tips.
  • No flow passes through an activity, a decision, or another flow: loops and bypasses are routed into free corridors beside the affected node.
  • Guards sit next to their own segment, never on top of a line or a box.
  • Every activity has an incoming and an outgoing flow; each path terminates at a final node.
